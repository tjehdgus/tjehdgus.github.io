From April to May 2026, a teammate and I entered Track 2 of the 2nd Fair Trade AI & Data Competition, run around the Korea Fair Trade Commission (KFTC). The task was to build a RAG system over 500 KFTC decisions. I owned the LLM side (LoRA training on EXAONE, generation evaluation) and part of the retrieval stack (contextual chunking, index normalisation, table conversion, reranker fusion). My teammate owned the embedding comparison and reranker fine-tuning.

This condenses a three-part build log on my Korean blog. Detailed experiments and code are in the original series.

## The rules decided the design first

The decisions came pre-split into 31,877 chunks. For every question, the system had to return exactly five evidence chunk IDs and an answer. Many violations zeroed the score.

| Rule | Penalty |
|---|---|
| Exactly five chunk IDs, no duplicates | Retrieval scored 0 |
| Original chunk IDs only (no re-chunking) | That chunk counted wrong |
| Under 30 seconds per question | Whole question scored 0 |
| Local LLM of 8B parameters or fewer | Disqualified |

I put this table at the top of the README and struck options off against it. Most decisions came from there.

- **Two embedding models, not five.** A five-model ensemble and a two-model ensemble had practically the same R@5 (0.5402 vs 0.5420), but took 29.4 s and 2.98 s.
- **Add context in front of chunks instead of re-chunking.** Failure analysis showed a 90% miss rate on chunks under 100 characters, and 46.4% of wrong hits were the chunk right next to the correct one. A table fragment like "fine | 1,000,000 KRW" says nothing about which case it belongs to. Since we could not re-cut chunks, I borrowed the idea behind Anthropic's Contextual Retrieval and indexed each chunk with document context prepended. R@5 rose by 8.45 percentage points.
- **Fuse two rerankers with RRF.** Reciprocal rank fusion merges models with different score scales by rank alone. Passing 6–8 candidates to the rerankers worked best.

The final pipeline fuses BM25 and two dense retrievers with RRF, fuses two rerankers again with RRF, and generates the answer with EXAONE 3.5 7.8B plus a LoRA adapter.

## Why we threw away our own 72.96

The official 200-question test set was hidden, so we built a 278-question eval set in the same format and made every keep-or-drop decision on it.

| Date | Change | Total |
|---|---|---|
| 4/24 | Baseline | 59.91 |
| 4/27 | + LoRA v1 | 63.82 |
| 4/29 | + Better embeddings | 67.14 |
| 4/30 | + Fine-tuned reranker | **72.96 (voided)** |
| 5/4 | Normalisation + two-reranker RRF | 67.39 |
| 5/5 | + Continued LoRA training | 67.76 |

On April 30 the retrieval score jumped 5.8 points in a single day, when one point a day had been hard. We found two leaks.

- **Embedding fine-tuning (my work).** To teach the model to separate neighbouring chunks, I built contrastive triplets using all 278 eval questions as queries. It had no effect, so I dropped it. In hindsight, that was lucky.
- **Reranker fine-tuning (my teammate's work).** The eval set was split 80/20 and the reranker trained on 222 questions. The hold-out check was fine, but the 72.96 came from re-running that model on all 278.

Both leaks happened because we had only one eval set, and it was the best-labelled QA data in the project. It was the first thing anyone looking for training data would grab. And a rising score invites less suspicion.

We voided the 72.96 and retrained using only a separate 1,500-question set generated with GPT-4o-mini. Since then I split dev and final eval sets from day one, and keep both the eval questions and their answer chunks out of training.

## What LoRA taught me: copying the surface pattern backfires

Generation used EXAONE 3.5 7.8B in 4-bit with a LoRA adapter (r 16, alpha 32). Training data came from 1,500 decision chunks, with questions and answers generated by GPT-4o-mini; it took four hours and cost $0.40.

| Version | Data | Generation score |
|---|---|---|
| Baseline | No LoRA | 28.53 |
| v1 | Free-form, 88 chars on average | **30.90** |
| v2 | Forced answer-pattern sentence, 54 chars | 23.73 |
| v3 | Fixed opening + free explanation, 110 chars | 24.43 |

Many reference answers began with the same phrase ("In this case, the respondent …"), so I expected that matching the format would raise token F1. It did the opposite. The questions ranged across fact checks, legal interpretation and sanctions, but training every answer to open with the same template produced answers that filled the template regardless of the question. Feeding more raw decision text (continued pre-training, or raw text mixed with QA) also scored below v1. The biggest generation gain remained the very first LoRA.

## If I did it again

- Write the rules table first and strike every option against it.
- Split dev and final eval sets from the start, and remove answer chunks from anything that can be trained on.
- When the score jumps in a day, find the cause before celebrating.
- Build training data that follows the distribution of answers, not the surface of a few of them.
