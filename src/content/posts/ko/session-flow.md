요즘은 Claude Code 세션 여러 개를 한 작업 폴더에 띄워 두고 역할을 나눠 일을 시킨다. 메인 세션이 일을 나누고, 다른 세션들이 각자 맡은 부분을 하면서 SendMessage로 결과를 주고받는다. 세션이 서너 개로 늘면 누가 누구에게 무슨 말을 했는지, 어떤 세션이 어떤 파일을 고쳤는지 따라가기 어려워진다. 그래서 이 흐름을 IDE 안에서 그림으로 보고 바로 개입할 수 있는 도구 Session Flow를 만들었다.

2026년 10월 7일 하루 동안 18개 커밋으로 v0.9.0까지 올렸다. 코드는 확장 쪽 JavaScript 약 2,350줄, 플러그인 약 410줄, 테스트 약 920줄이다. ([GitHub](https://github.com/tjehdgus/session-flow))

## 구조: 서버 없이 파일만

- **Claude Code 플러그인**: hook으로 세션 활동(질문, 툴 호출, 서브에이전트 위임, 세션 간 메시지, 파일 수정 전/후)을 `~/.session-flow/`에 기록한다.
- **VS Code 확장**: 그 파일을 감시하면서 세션 그래프, 이벤트 목록, 파일 diff를 보여준다.

혼자 쓰는 도구에 서버를 붙이면 띄우고 관리하는 일이 생기고, 원격 SSH 환경에서 그대로 동작하게 만들기도 어렵다. 파일만 쓰면 세션이 도는 머신 어디서든 같은 방식으로 동작한다.

## 원칙 하나: 관찰 도구가 본 작업을 막으면 안 된다

SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, SubagentStart/Stop 같은 hook에 같은 기록 스크립트를 걸고, 이벤트마다 한 줄씩 `events.jsonl`에 붙인다. 기록 스크립트는 예외가 나도 `errors.log`에만 남기고 항상 exit 0으로 끝난다. 관찰 도구 때문에 작업이 멈추면 결국 안 쓰게 되기 때문이다.

파일 diff를 보려면 수정 전 내용이 필요하다. Edit 툴에는 바뀐 부분이 있지만 Write는 그렇지 않아서, 수정 툴이 불리면 PreToolUse에서 "전", PostToolUse에서 "후" 스냅샷을 남긴다. diff는 확장에 npm 의존성을 넣지 않으려고 직접 짰다(78줄). 공통 앞뒤를 잘라내고 남은 가운데만 LCS로 비교한 뒤 git 스타일 hunk로 묶는다. 코드 수정은 대부분 파일 일부만 바꾸기 때문에 앞뒤를 자르는 것만으로 비교량이 크게 준다.

## 가장 오래 헤맨 문제: 이 주소는 어느 세션인가

진짜 보고 싶었던 건 세션 사이의 흐름이었다. 보내는 쪽은 PreToolUse에서 SendMessage의 수신자를 기록하면 된다. 문제는 받는 쪽이었다. 다른 세션에서 온 메시지의 발신자가 세션 ID가 아니라 소켓 주소나 핸들로 들어왔고, 화살표 하나를 그리려면 "이 주소가 어느 세션인가"를 알아내야 했다.

여기에 커밋 다섯 개가 들어갔다. 메시지 본문을 비교해 자동 연결하기, 사용자가 직접 이름 붙이기, 모르는 주소를 "기타" 노드로 묶기, 각 세션이 자기 소켓 주소를 기록하게 하기, ListAgents 결과로 핸들 학습하기. 점점 정확해졌지만 코드를 보면 추측하는 경로가 계속 늘고 있었다.

## 하네스를 만들다가 설계를 갈아엎었다

오후에는 그래프를 보기만 하는 게 아니라 설계도 하는 "하네스" 기능을 넣었다. 작업 폴더의 세션들을 멤버, 역할, 메인, 메시지 방향으로 묶어 저장하면, hook이 각 세션에 "너는 어떤 역할이고, 누구와는 메인을 거쳐서 얘기해라"를 안내한다. 매 질문마다 넣으면 컨텍스트가 지저분해지니 설정이 바뀌었을 때만 다시 넣는다.

그런데 멤버를 세션 ID로 적으면 재시작할 때마다 ID가 바뀌고, 다른 PC에서는 아예 맞지 않았다. 그래서 v0.6.0에서 멤버를 세션의 `/rename` 이름으로 바꿨다. 이 이름은 SendMessage 수신자로 그대로 쓸 수 있고 재시작해도 유지된다. 커밋 메시지에는 "이름이 곧 메시지 주소, 주소 추측 제거"라고 적었다. 이 커밋에서 그래프 코드 842줄을 지우고 화면을 새로 썼다. 추가 1,556줄, 삭제 1,757줄로 지운 쪽이 더 많았다.

시스템이 이미 사람이 붙이는 고정 이름을 제공한다면, 내부 ID와 주소를 추측해서 맞추는 것보다 그 이름을 기준으로 삼는 편이 훨씬 단순하다. 처음부터 그렇게 했어야 했다.

## 막을 때는 느슨하게

하네스에서 강제 모드를 켜면 정한 방향 밖으로 가는 SendMessage를 PreToolUse에서 거부한다. 두 가지는 일부러 느슨하게 뒀다.

- **어느 세션인지 모르는 주소는 막지 않는다.** 주소 해석이 틀려서 정상 메시지를 막는 것이 규칙 위반을 놓치는 것보다 더 나쁘다.
- **받은 메시지에 대한 답장은 허용한다.** 메인에서 멤버로 가는 방향만 정했는데 멤버가 결과 보고를 못 하면 하네스가 일을 방해한다.

막을 때는 거부 이유와 보낼 수 있는 대상을 같이 알려줘서, 세션이 스스로 메인을 거쳐 다시 보내게 했다. 하네스 파일 작성 자체도 `/session-flow:harness` 스킬로 세션에게 맡길 수 있게 했다. 이미 역할을 나눠 일하는 세션이 그 구성을 가장 잘 알기 때문이다.

## 배운 것

- 관찰 도구는 실패해도 본 작업을 막지 않게 만든다.
- 외부 의존성이 없으면 원격 환경에서도 그대로 돈다.
- 추측으로 맞추는 경로가 늘어나기 시작하면, 시스템이 이미 주는 고정 식별자가 있는지부터 다시 본다.
- 차단 규칙은 오탐 비용이 미탐 비용보다 클 때 느슨하게 시작한다.
