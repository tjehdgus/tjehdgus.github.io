## 초록

이전 회사(제조 기업)에서 2026년 1~2월에 영업 담당자용 원가율 예측 시뮬레이터를 만들었다. 입력은 품목, 거래처, 부서, 담당자, 단가, 수량이고 출력은 예측 원가율, 적자 여부, 위험 등급, 흑자 전환에 필요한 단가다. 원가율을 직접 예측하면 사용자가 바꾸는 단가에 모델이 일관되게 반응한다는 보장이 없어서, 타깃을 단가와 독립적인 단위원가(매출원가 / 수량)로 바꾸고 원가율은 `예측 단위원가 / 입력 단가`로 계산했다. 모델은 RandomForest 회귀이고, 품목×거래처 조합의 최근 3건 가중 이동평균과 모델 예측을 기하평균으로 섞었다. 이력이 없는 신규 거래처는 품목 피처 4개만 쓰는 별도 모델로 처리했다. 서비스는 FastAPI로 구성해 Azure Container Apps에 배포했고, 2월 개정판에서 사용자 관리와 설정 분리를 넣었다. 레포에 학습·검증 로그가 없어 정량 성능은 싣지 않는다.

## 1. 문제 정의

영업 담당자가 견적을 내기 전에 "이 품목을 이 거래처에 이 단가와 수량으로 팔면 적자인가"를 확인하는 도구가 필요했다. 회사 기준으로 원가율 85% 이상인 거래를 적자로 분류한다.

| 항목 | 내용 |
|---|---|
| 입력 | 품목 코드, 거래처, 부서, 담당자, 단가, 수량 (신규 거래처는 품목 코드, 단가, 수량) |
| 모델 출력 | 예측 단위원가 |
| 계산 출력 | 예측 원가율, 적자 여부, 위험 등급 5단계, 단가 +10/20/30% 시 원가율, 흑자 전환 필요 단가와 인상률, 수량×단가 그리드 |
| 판정 기준 | `적자 = 원가율 >= 85` |

```text
원가율(%)      = 매출원가 / 매출 * 100
단위원가        = 매출원가 / 수량
예측 원가율(%)  = 예측 단위원가 / 입력 단가 * 100
필요 단가       = 예측 단위원가 / 0.85
```

제약 조건은 두 가지였다. 사용자는 단가를 반복해서 바꿔 보는데, 원가율을 타깃으로 두면 학습 데이터에 없던 단가 구간에서 원가율이 단가에 반비례한다는 관계를 모델이 지킨다는 보장이 없다. 또 결과를 영업 담당자에게 설명할 수 있어야 했다. 단위원가를 예측하면 "모델은 이 거래의 단위원가를 X로 보고, 입력한 단가 대비 Y%다"로 설명이 끝난다.

## 2. 데이터

사내 판매 실적 테이블을 CSV로 받아 썼다. 원본 데이터와 학습된 모델 파일은 레포에서 제외되어 있고(`.gitignore`의 `data/`), 건수와 기간은 레포로 확인할 수 없어 적지 않는다. 아래는 `main.py`의 로딩 코드에서 확인한 컬럼 구성과 전처리다.

| 구분 | 컬럼 |
|---|---|
| 식별·범주 | 품목 코드, 품목명, 품목 분류(대/중/소), 거래처, 부서, 담당자, 판매 단위 |
| 수치 | 판매 단가, 수량, 원화 판매금액, 매출원가, 원가율(%) |
| 시간 | 기간 컬럼 1개 (정렬 키) |

전처리 순서는 다음과 같다.

1. 거래처가 비어 있는 행 제거
2. 단가·수량을 숫자로 변환하고 변환 실패 행 제거
3. 단가, 수량, 판매금액이 모두 0보다 큰 행만 유지
4. 기간, 품목 코드 순으로 정렬
5. 파생 컬럼 생성: `품목_거래처` 조합 키, `적자여부 = 원가율 >= 85`, `단위원가 = 매출원가 / 수량`

서버는 시작할 때 이 테이블로 그룹 통계, lag, 이동평균 테이블과 드롭다운용 관계 맵(품목 → 거래처 → 부서 → 담당자)을 한 번 만들어 메모리에 둔다. 관계 맵은 실제로 거래한 적 없는 조합을 입력하지 못하게 다음 드롭다운 목록을 좁히는 데 쓴다.

## 3. 방법

### 3.1 전체 파이프라인

```text
[서버 시작]
판매 실적 CSV
  → 전처리 / 단위원가·적자여부 파생
  ├─ 그룹 통계 (품목, 거래처, 품목×거래처, 부서, 담당자)
  ├─ 시계열 통계 (lag 1~3, 이동평균 3/5/10, 이동표준편차 3/5)
  └─ 관계 맵 (품목 → 거래처 → 부서 → 담당자)

[예측 요청]
입력 (품목, 거래처, 부서, 담당자, 단가, 수량)
  → 피처 조립 (통계 테이블 조회 + 라벨 인코딩 + 로그 수량 + 시기)
  → RandomForest 단위원가 예측
  → 최근 3건 WMA와 기하평균 보정 (이력 없으면 모델 값 그대로)
  → 원가율 = 예측 단위원가 / 단가 * 100
  ├─ 적자 판정, 위험 등급, 필요 단가
  ├─ 단가 인상 시뮬레이션 (모델 재호출 없음)
  ├─ 수량×단가 그리드 (수량 행마다 모델 호출)
  └─ LLM 해설 (gpt-4o-mini)
```

- 통계 테이블: 예측 시점에 피처를 조립하기 위해 과거 실적을 그룹별로 미리 요약한다.
- 피처 조립: 조회 결과가 없으면 대체값으로 채운다(3.3).
- 단위원가 예측: 기존 거래처 모델과 신규 거래처 모델 중 하나를 탄다.
- 원가율 계산: 단가는 모델 입력이 아니라 이 단계에서만 쓰인다.

### 3.2 타깃 재정의: 원가율 대신 단위원가

사용자가 조작하는 변수(단가)를 모델 밖으로 뺐다. 모델은 단위원가만 예측하고 원가율과 파생값은 나눗셈으로 계산한다.

`main.py`
```python
        판매금액 = 단가 * 수량
        예측_원가율 = (예측_단위원가 / 단가) * 100
        적자여부 = 예측_원가율 >= PROFIT_THRESHOLD
        
        if 예측_원가율 >= 100: 위험등급 = "매우위험"
        elif 예측_원가율 >= 90: 위험등급 = "고위험"
        elif 예측_원가율 >= 85: 위험등급 = "주의"
        elif 예측_원가율 >= 75: 위험등급 = "관심"
        else: 위험등급 = "안전"
        
        원가율_10up = (예측_단위원가 / (단가 * 1.1)) * 100
        원가율_20up = (예측_단위원가 / (단가 * 1.2)) * 100
        원가율_30up = (예측_단위원가 / (단가 * 1.3)) * 100
        필요단가 = 예측_단위원가 / 0.85
        필요인상률 = ((필요단가 / 단가) - 1) * 100
```

이 구조에서 원가율은 단가에 대해 항상 단조 감소하고, 단가 변경 시뮬레이션은 모델을 다시 부르지 않는다. 수량은 단위원가에 영향을 주는 입력(`log_수량`)이라 수량×단가 그리드에서는 수량 5개 행(0.5, 1, 2, 5, 10배)마다 모델을 호출하고, 단가 6개 열(-20%~+30%)은 나눗셈으로 채운다.

### 3.3 피처 설계

기존 거래처 모델의 추론 코드는 다음 다섯 묶음, 40개 후보 피처를 조립한 뒤 모델 아티팩트에 저장된 `feature_cols` 순서로 선택한다.

| 묶음 | 피처 | 개수 |
|---|---|---|
| 범주 인코딩 | 품목, 거래처, 부서, 담당자 라벨 인코딩 (미등록 값은 -1) | 4 |
| 수량·시기 | `log1p(수량)`, 연, 월, 분기, 월 sin/cos | 6 |
| 그룹 통계 | 품목, 거래처, 담당자, 부서, 품목×거래처별 평균 단위원가, 표준편차, 거래 건수 | 15 |
| lag | 품목 lag1~3, 거래처 lag1~2, 품목×거래처 lag1 | 6 |
| 이동 통계·추세 | 품목 MA3/5/10, 품목 MSTD3/5, 거래처 MA3/5, 품목·거래처 trend(lag1 - 평균) | 9 |

품목 평균 단위원가와 표준편차, 평균 원가율은 마지막 거래를 빼고 계산한다. 마지막 거래가 포함된 평균을 그 거래의 예측에 쓰면 정답이 피처에 섞이기 때문이다.

`main.py`
```python
def calc_품번_stats(group):
    if len(group) > 1:
        평균단위원가 = group['단위원가'].iloc[:-1].mean()
        단위원가_std = group['단위원가'].iloc[:-1].std()
    else:
        평균단위원가 = group['단위원가'].iloc[0]
        단위원가_std = 0
    return pd.Series({
        '품번_평균단위원가': 평균단위원가,
        '품번_단위원가_std': 단위원가_std,
        '품번_거래건수': len(group),
        '품번_최근단위원가': group['단위원가'].iloc[-1],
        '품번_평균원가율': group['원가율(%)'].iloc[:-1].mean() if len(group) > 1 else group['원가율(%)'].iloc[0],
        '품번_최근원가율': group['원가율(%)'].iloc[-1],
    })
```

결측 처리는 계층적이다. 품목 lag와 이동평균이 없으면 품목 평균으로, 거래처 lag가 없으면 거래처 평균으로, 그룹 자체가 없으면 전체 평균 단위원가로 채우고, 그래도 NaN이면 -999를 넣는다.

### 3.4 최근 실적 기하평균 보정

RandomForest는 그룹 평균 피처에 크게 기대므로 최근 원가가 크게 움직인 조합에서는 과거 평균 쪽으로 끌려간다. 이를 보정하기 위해 품목×거래처 조합의 최근 3건 단위원가로 가중 이동평균(가중치 1, 2, 3, 최신이 3)을 구하고 모델 예측과 기하평균을 냈다.

`main.py`
```python
    품번_거래처_recent = df[(df['품번'] == 품번) & (df['거래처'] == 거래처)].sort_values('년월', ascending=False)
    
    if len(품번_거래처_recent) >= 1:
        recent_values = 품번_거래처_recent['단위원가'].head(3).values
        if len(recent_values) == 1:
            품번_거래처_wma3 = recent_values[0]
        elif len(recent_values) == 2:
            품번_거래처_wma3 = np.average(recent_values, weights=[2, 3][-len(recent_values):])
        else:
            품번_거래처_wma3 = np.average(recent_values, weights=[1, 2, 3])
        예측_단위원가 = (품번_거래처_wma3 ** 0.5) * (예측_단위원가_rf ** 0.5)
        예측방식 = "Hybrid 기하평균 (최근값^0.5 × 모델^0.5)"
    else:
        예측_단위원가 = 예측_단위원가_rf
        예측방식 = "모델 Only"
```

산술평균 대신 기하평균을 쓴 이유는 품목마다 단위원가의 자릿수가 크게 달라서, 두 값을 비율로 섞는 쪽이 한쪽 값이 튈 때 덜 흔들리기 때문이다. 응답의 `예측방식` 필드로 혼합 여부를 화면에 표시했다.

### 3.5 신규 거래처 모델

이력이 없는 거래처를 기존 모델에 넣으면 거래처·부서·담당자 관련 피처 21개가 미등록 인코딩(-1)이나 전체 평균 같은 대체값으로 채워진다. 기존 모델이 거래처 간 차이로 학습한 분기들이 의미 없는 입력을 받게 되므로, 품목 정보만 쓰는 모델을 따로 학습해 두 개의 아티팩트로 배포했다.

`main.py`
```python
    features = pd.DataFrame([{
        '품번_encoded': 품번_encoded,
        'log_수량': np.log1p(수량),
        '품번_평균단위원가': 품번_평균단위원가 if not pd.isna(품번_평균단위원가) else 전체_평균단위원가_new,
        '품번_거래건수': 품번_거래건수 if not pd.isna(품번_거래건수) else 0,
    }])

    features = features[feature_cols_new]
    예측_단위원가_rf = model_new.predict(features)[0]
```

보정도 같은 방식이되, 기준을 품목×거래처 조합이 아니라 품목 전체의 최근 3건으로 바꿨다. "신규 거래처" 탭은 별도 엔드포인트를 호출하고 상세 분석에서도 품목 이력만 보여준다.

### 3.6 LLM 해설

예측 결과 옆에 Azure OpenAI의 gpt-4o-mini로 만든 해설을 붙였다(`max_tokens=1500`, `temperature=0.5`). 프롬프트에는 예측 원가율, 단가 인상 시뮬레이션, 품목과 거래처의 과거 적자 빈도, 품목의 거래처별 현황과 거래처의 품목별 현황(각 상위 15개)을 넣고 종합 평가, 품목 분석, 거래처 분석, 시뮬레이션 참고의 4개 섹션으로 쓰게 했다. 단위(%와 원) 구분을 시스템 프롬프트에 명시하고, 이 거래의 예측 원가율을 프롬프트 앞뒤에 반복했다. "~해야 합니다" 같은 지시 표현은 금지해 판단을 영업 담당자에게 남겼고, 적자 비율은 확률과 헷갈리지 않도록 "N건 중 M건(X%)" 형식으로 쓰게 했다.

### 3.7 서비스 구조와 사용자 관리

백엔드는 FastAPI, 프론트엔드는 단일 HTML 페이지다. Docker 이미지로 빌드해 Azure Container Apps에 올렸고(0.5 vCPU, 1 GiB, 레플리카 1~3), 모델 파일과 실적 데이터는 Azure File 볼륨을 `DATA_DIR`로 마운트해 읽는다. 데이터 갱신 때 이미지를 다시 빌드하지 않기 위해서다.

2월 개정판에서는 사내 다른 도구와 같이 쓰는 통합 사용자 관리 모듈을 붙이고 환경변수를 `config.py` 하나로 모았다. 사용자·권한·세션은 Cosmos DB에 둔다.

| 항목 | 구현 |
|---|---|
| 비밀번호 | bcrypt 해시. 구 SHA-256 해시로 로그인 성공 시 bcrypt로 자동 재해시 |
| 비밀번호 정책 | 8자 이상, 대·소문자, 숫자, 특수문자 각 1개 이상 |
| 로그인 제한 | 5회 실패 시 15분 잠금 |
| 권한 | 앱별 권한 레코드, 역할 레벨 `admin > staff > viewer` |
| 감사 로그 | 로그인 성공·실패·잠금·해시 마이그레이션 기록 |
| 관리자 비밀번호 | 운영 모드에서 환경변수가 없으면 기동 시 오류, 로컬에서는 임시 비밀번호 생성 |

## 4. 실험

### 4.1 실험 설정

레포에는 추론 서버 코드만 있고 모델 학습 스크립트, 검증 분할, 하이퍼파라미터, 평가 로그는 포함되어 있지 않다. 학습된 모델은 `model`, `label_encoders`, `feature_cols`를 담은 pickle 아티팩트 두 개(기존 거래처용, 신규 거래처용)로 배포됐다. 두 모델 모두 RandomForest 회귀이고 타깃은 단위원가다. 기존 거래처 모델은 후보 40개 중 `feature_cols`를, 신규 거래처 모델은 피처 4개를 쓴다. 보정 기준은 각각 품목×거래처 최근 3건과 품목 최근 3건이며 기하평균 지수는 둘 다 0.5로 고정되어 있다. 이 절은 레포에서 확인 가능한 엔드포인트별 동작을 정리한다.

### 4.2 결과

정량 성능(R², MAPE 등)은 레포에서 확인할 수 있는 근거가 없어 싣지 않는다. 코드에서 확인되는 엔드포인트별 계산량은 다음과 같다.

| 기능 | 엔드포인트 | 모델 호출 수 | 나머지 계산 |
|---|---|---|---|
| 단건 예측 | `/api/predict_cost_rate` | 1 | 원가율, 위험 등급, +10/20/30%, 필요 단가 |
| 임의 단가 시뮬레이션 | `/api/simulate_custom_price` | 0 | 나눗셈 1회 |
| 수량×단가 그리드 | `/api/simulate_price_quantity_grid` | 6 (수량 5행 + 기준 1) | 30칸 원가율과 판정 |

### 4.3 비교 실험

레포에는 아래 변형들의 정량 비교가 남아 있지 않다. 표는 각 설계 선택이 시뮬레이터 동작에 주는 차이를 코드 기준으로 정리한 것이다.

| 변형 | 단가 변경 시 모델 재호출 | 단가에 대한 원가율 단조성 | 비고 |
|---|---|---|---|
| 원가율 직접 회귀 | 필요 | 보장 안 됨 | 채택 안 함 |
| 85% 기준 적자/흑자 분류 | 필요 | 보장 안 됨 | 필요 단가 산출 불가 |
| 단위원가 회귀 + 나눗셈 (채택) | 불필요 | 보장 | 필요 단가를 닫힌 식으로 계산 |
| 모델 단독 | - | - | 최근 원가 변동을 그룹 평균 쪽으로 끌어당김 |
| 모델 + 최근 3건 WMA 기하평균 (채택) | - | - | 조합 이력 있을 때만 적용 |
| 신규 거래처를 기존 모델로 처리 | - | - | 거래처 계열 피처 21개가 대체값 |

## 5. 한계와 향후 과제

- **검증 재현성.** 학습·검증 코드와 로그가 레포에 없어 성능을 재현하거나 변형 간 비교를 다시 할 수 없다.
- **통계 테이블의 시점.** 품목 평균은 마지막 거래를 빼고 만들지만 거래처 통계, lag, 이동평균은 가장 최근 거래까지 포함한다. 새 거래를 예측하는 운영에서는 맞는 처리지만, 같은 테이블로 과거 거래를 재예측해 평가하면 정답이 섞인다. 평가 시에는 기준 시점 이전 데이터로 테이블을 다시 만들어야 한다.
- **연도 피처의 외삽.** 연·월 피처에 요청 시각을 넣는다. 학습 데이터의 마지막 연도를 넘으면 트리 모델은 사실상 마지막 연도로 취급한다. 연도는 빼거나 경과 기간으로 바꾸는 편이 낫다.
- **혼합 지수 고정.** 기하평균 지수 0.5는 코드에 고정되어 있고, 이 값을 정한 검증 기록이 레포에 없다. 품목별 원가 변동성에 따라 지수를 바꾸거나 후보 값을 시간 분할 검증으로 비교해야 한다.
- **서빙 구조.** 시뮬레이션·상세 분석·LLM 해설 엔드포인트 일부에 로그인 확인이 빠져 있고, 로그인 실패 횟수를 프로세스 메모리에 저장해 레플리카가 여러 개일 때 잠금이 공유되지 않는다. 인증 검사를 의존성으로 통일하고 시도 기록을 공용 저장소로 옮겨야 한다.
