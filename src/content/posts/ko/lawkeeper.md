## 초록

LawKeeper는 사용자가 법적 상황을 설명하면 판례, 법령, 약관, 상담 사례를 검색해 근거와 함께 자문을 생성하는 법률 상담 RAG 챗봇이다. 4인 팀이 개발해 PC·모바일 웹으로 배포했다. 형식이 다른 원천 데이터(JSON, CSV, PDF)를 `{id, content, metadata}` 구조로 통일해 `jhgan/ko-sbert-nli`로 5개 컬렉션에 적재했고, 컬렉션별 top-5를 GPT-4o-mini에 전달한다. 핵심 과제는 사건 정보가 없는 후속 질문의 검색이었다. 10개 대화 루프 버전을 거쳐, 충분성 판단을 통과한 사건 설명을 요약해 고정하고 후속 질문마다 `요약(고정 사건 + 현재 질문)`으로 검색하는 구조로 정리했다. 레포에 정량 평가셋이 없어 비교는 코드에서 확인되는 설계 차이로 한정한다.

## 1. 문제 정의

**과제.** 일반 사용자의 사건 설명에 조문·판례 근거가 있는 자문을 만들고, 후속 질문에도 같은 사건 맥락으로 답한다.

| 단계 | 입력 | 출력 |
|---|---|---|
| 초기 상담 | 사건 설명(여러 턴 누적 가능) | 부족하면 추가 정보 질문 1문장, 충분하면 8개 항목 초기 자문 |
| 후속 상담 | 후속 질문 + 고정 사건 요약 + 대화 이력 | 질문에 직접 답하는 후속 자문 |

**평가.** 레포에는 평가셋, 정답 문서 라벨, 검색 지표 코드가 없다. 버전 채택은 질의를 직접 넣어 결과를 확인하는 방식이었다(개발 기록 기준). 이 글은 두 설계 목표, 즉 검색 결과에 여러 종류 근거가 함께 들어가는가(목표 1, 출처 다양성)와 후속 검색 쿼리에 사건 정보가 항상 포함되는가(목표 2, 맥락 유지)를 기준으로 코드 수준에서 비교한다.

**제약.** 생성은 모든 버전에서 `gpt-4o-mini`, 임베딩은 로컬 SentenceTransformer, 저장소는 ChromaDB `PersistentClient`다. ChromaDB 메타데이터는 스칼라 값만 받는다. 배포는 Google Cloud Run, 로그는 BigQuery다(README).

## 2. 데이터

원천은 공개 데이터셋의 판결서·약관·상황별 판례 JSON, 대한법률구조공단 법률 상담·사이버 상담 게시판을 Selenium으로 수집한 CSV, 공개 QA JSON(instruction 형식, easylaw), 6법(헌법, 민법, 형법, 상법, 민사소송법, 형사소송법) 법전 PDF다. 형식과 관계없이 본문과 메타데이터를 분리해 문서 하나를 JSON 하나로 저장했다.

| 컬렉션 | 원천 | 본문 구성 | 주요 메타데이터 | 청킹 |
|---|---|---|---|---|
| `legal_laws` | 6법 PDF | 조문 1개 | 법령명, 조문 | 조문 단위 |
| `legal_rag_docs_kosbert` | 상황별 판례·심결례 | `[판시사항]`, `[판결요지]`, `[요약]`, `[질문]/[답변]` 등 태그 결합 | 사건번호, 법원명, 선고일, 키워드, 참조조문, 참조판례 | 없음 |
| `legal_cases` | 판결서 | `취지`, `사실`, `판단` 결합 | 사건번호, 선고일, 사건명, 법원명, 사건유형 | 없음 |
| `terms_clauses` | 약관 | 약관분야 + 조항 + 유불리판단 + 위법성 근거 + 관련 법령 | 약관분야, 공정위 심결례, 유불리판단 | 없음, 100자 미만 제외 |
| `legal_qa_rag_docs` | 크롤링 CSV, 공개 QA | `Q: ... A: ...` 또는 `### Instruction / ### Output` | 원본 컬럼, source_file | 400자 / 오버랩 100 |

건수는 약관 적재 스크립트 출력 문구의 JSON 8,997개 외에는 레포에서 확인되지 않는다.

전처리는 네 갈래다. 판결서·약관은 숫자 코드값을 명세 기반 매핑으로 텍스트화하고(`caseField` "1"→"민사", `clauseField` "5"→"임대차계약") 약관 키를 한글화했다(`02_`). 상황별 판례는 원문(TS/VS)과 라벨(TL/VL)을 파일명 기준 1:1 병합한 뒤 섹션 태그로 본문을 만들고 참조조문·판례를 메타데이터로 옮겼다(`04_`, `05_`). 상담 Q&A는 JSON 구조별로 분기하고 CSV는 행 하나를 문서 하나로 만들었다(`07_`). 코드값을 그대로 임베딩하면 "임대차계약" 같은 단어가 문서에 없어 질의와 맞물리지 않는다.

## 3. 방법

### 3.1 전체 파이프라인

```text
[오프라인 적재]
 ├─ 판결서·약관 JSON ── 코드값→텍스트 매핑 ──────────────┐
 ├─ 상황별 판례 JSON ── 원문/라벨 병합 → 태그 본문 ───────┤
 ├─ 상담 Q&A ───────── Q/A 문서화 → 400/100 청킹 ────────┤
 └─ 6법 PDF ────────── 글꼴 기반 조문 추출 → 정제 ────────┘
                            ↓
     {id, content, metadata} → ko-sbert-nli → ChromaDB 5개 컬렉션

[온라인 대화]
 ├─ 초기 모드: 사건 설명 누적 → 충분성 판단
 │    ├─ 부족 → 추가 질문 1문장
 │    └─ 충분 → 사건 요약 고정 → 5개 컬렉션 × top-5 → 초기 자문
 └─ 자문 이후: 요약(고정 사건 + 질문) → 5개 컬렉션 × top-5
              + 이력 요약 → 후속 자문
```

- 충분성 판단: GPT가 `YES` 또는 추가 질문 한 문장을 반환한다.
- 사건 고정: 판단 통과 시점의 설명 요약을 이후 모든 검색의 기준으로 쓴다.
- 질의 재작성: 후속 질문을 고정 사건과 합쳐 다시 요약해 검색한다.

### 3.2 메타데이터 정규화

판례의 키워드, 참조조문, 참조판례는 리스트라서 ChromaDB에 그대로 넣을 수 없다. 적재 직전에 JSON 문자열로 펴고 `None`은 빈 문자열로 바꿨다. 판례와 Q&A 적재 스크립트가 같은 `flatten_metadata` 함수를 쓴다. 청크 적재(`09_`)는 청크마다 원문 메타데이터를 복제하고 ID를 `원본파일명_chunk{i}`로 만들어 출처를 추적한다.

### 3.3 법전 PDF의 조문 경계 검출

법령별 시작·끝 페이지를 딕셔너리로 두고(예: 민법 21~132쪽) 그 범위만 처리했다. "제750조"는 본문에서도 "제750조에 따라"처럼 반복되어 정규식만으로는 제목과 인용을 구분할 수 없다. 조문 제목 span만 특정 글꼴·크기·플래그를 쓰는 점을 이용해 텍스트 패턴과 글꼴 조건을 함께 걸었다.

`code/19_법전 json ocr 코드 수정 제거 치환 추가 - 최종.py`
```python
                    is_title_candidate = (
                        raw_text.startswith("제") and
                        "조" in raw_text and
                        font == "H2gtrE" and
                        abs(size - 7.79) < 0.05 and
                        flags == 4
                    )
```

제목이 `제3조(정의`에서 끊기면 닫는 괄호가 나올 때까지 다음 span을 이어 붙였고, 장·절 제목은 본문에서 뺐다. 후처리로 괄호 안 한자, 교재 바닥글, `- 301 -` 형태 쪽 번호를 지우고 원문자 ①~㊿를 "1항"~"50항"으로 바꿨다. 사용자는 질의에 원문자를 쓰지 않으므로 본문 표기를 질의 쪽에 맞춘 것이다. 추출 과정에서 무너진 띄어쓰기는 PyKoSpacing으로 교정했다(`21_`).

### 3.4 컬렉션 분리와 임베딩 모델 통일

한 컬렉션에 모두 넣으면 질의와 문체가 비슷한 상담 Q&A가 상위를 차지해 프롬프트가 요구하는 조문·판례 근거가 빠지기 쉽다. 컬렉션별로 top-K를 뽑으면 다섯 종류 근거가 항상 함께 들어가고, 각 문서 앞에 `[출처: legal_cases]`처럼 컬렉션 이름을 붙여 LLM이 근거 종류를 구분하게 했다.

초기 적재 코드는 컬렉션마다 모델이 달랐다(판결서 `jhgan/ko-sbert-nli`, 약관 `dragonkue/snowflake-arctic-embed-l-v2.0-ko`, 상황별 판례 `all-MiniLM-L6-v2`). 질의는 한 번만 임베딩해 모든 컬렉션을 조회하므로 모델이 다르면 벡터 공간이 어긋나고 차원이 다르면 조회가 실패한다. 최종 코드는 `jhgan/ko-sbert-nli` 하나로 통일했고 판례 컬렉션 이름도 `legal_rag_docs_kosbert`로 바뀌었다.

### 3.5 검색: 거리 임계값에서 컬렉션별 top-K로

첫 구현(`13_`)은 컬렉션마다 3개를 가져와 점수 0.5 이상만 남겼다.

`code/13_크로마디비 4개 RAG 구현 코드 임계값(쓰레스홀스) 0.5 프롬프트 적용.py`
```python
threshold = 0.5  # ✅ 유사도 임계값 설정
all_docs = []

for collection in collections:
    results = collection.query(query_embeddings=[query_embedding], n_results=N_RESULTS)
    docs = results["documents"][0] if results["documents"] else []
    scores = results["distances"][0] if results["distances"] else []

    for doc, score in zip(docs, scores):
        if score >= threshold:
            all_docs.append(doc)
```

ChromaDB `distances`는 작을수록 가까우므로 이 필터는 가까운 문서를 버린다. `hnsw:space` 기본값은 L2인데 cosine을 지정한 것은 약관 컬렉션뿐이라 척도도 컬렉션마다 달랐다. 임계값 0.3(`14_`, `15_`), 점수 출력 디버깅(`17_`)을 거쳐 `22_`부터 임계값을 제거했다. top-K는 3, 10을 거쳐 최종 5이고, 한 번에 최대 25개 문서가 프롬프트에 들어간다.

### 3.6 멀티턴 상태 관리와 후속 질문 검색

**충분성 판단.** 초기 모드에서는 입력을 누적하고 요약본으로 자문 가능 여부를 묻는다. 프롬프트는 "간결하더라도 법적으로 문제가 될 만한 사실이 드러나면 YES"로 기준을 낮춰 추가 질문 반복을 줄였다. "모르겠다", "없다" 같은 부정 표현이 있으면서 30단어를 넘으면 GPT 판단 없이 `YES`로 처리한다.

**사건 고정과 질의 재작성.** `YES` 시점의 누적 설명을 요약해 고정하고, 후속 질문은 여기에 섞지 않는다. "고소하면 얼마나 걸려요?"를 그대로 임베딩하면 "고소", "기간"에 가까운 무관한 문서가 올라오므로, 고정 요약과 질문을 합쳐 2~3줄로 다시 요약한 문장을 쿼리로 쓴다. 이전 후속 질문은 쿼리에 넣지 않는다.

`code/28_FAST API.py`
```python
    if advice_given:
        search_query = summarize_context(fixed_case_context + "\n" + question)
        document_context = search_documents(search_query, N_RESULTS)
        answer = generate_followup_rag_response(question, fixed_case_context, document_context, chat_history)
        chat_history.append({"role": "user", "content": question})
        chat_history.append({"role": "assistant", "content": answer})
        return answer
```

**이력 요약.** 생성에는 최근 10개 메시지를 300자씩 잘라 GPT로 요약한 결과를 사건 요약, 검색 문서, 질문과 함께 넘긴다. LLM 호출은 초기 자문 턴 최대 4회(요약, 판단, 사건 요약, 자문), 후속 턴 3회(쿼리 재작성, 이력 요약, 답변)다.

### 3.7 프롬프트와 생성 설정

초기 자문은 상황 정리 후 8개 항목(법적 판단, 판례 적용 가능성, 실무적 조언, 현실적 선택지, 즉시 조치, 주의사항, 상담 정리, 다음 단계 준비)을 고정 형식으로 요구한다. 후속 자문은 형식을 강제하지 않고 질문에 직접 답하도록 했으며, 기존 자문 형식을 반복하지 말라는 문장은 `16_`부터 들어 있다.

| 호출 | temperature | max_tokens |
|---|---|---|
| 사건·쿼리 요약 | 0.3 | 100 |
| 이력 요약 | 0.2 | 100 |
| 충분성 판단 | 0.7 | 100 |
| 초기 자문 | 0.5 | 1500 |
| 후속 자문 | 0.6 | 800 |

### 3.8 서빙

`28_FAST API.py`는 웹 서버가 호출하는 `ask_ai(question)`과 CLI 루프를 담은 모듈이다. README와 발표자료에는 Cloud Run 배포, BigQuery 로깅, 캐시, 병렬 검색, 세션 관리 클래스가 적혀 있으나 서버 코드는 레포에 없다.

## 4. 실험

### 4.1 실험 설정

- 비교 대상: 대화 루프 10개 버전(`13`~`16`, `22`~`26`, `28`)과 검색 디버깅 버전 `17`.
- 고정 요소: `gpt-4o-mini`, `jhgan/ko-sbert-nli`.
- 평가 방식: 정량 평가셋 없음. 검색 쿼리와 검색 결과가 어떻게 만들어지고 LLM에 전달되는지를 코드 경로로 비교한다.
- 적재 설정: 판결서 임베딩 배치 32, 판례·Q&A 추가 배치 500, Q&A 청킹 400/100. 약관 컬렉션은 `hnsw:space=cosine`, `M=32`, `construction_ef=400`, `search_ef=50`.

### 4.2 결과

| 구성 요소 | 최종 설정 (`28_`) |
|---|---|
| 컬렉션 | 5개 |
| 검색 | 컬렉션별 top-5, 임계값 없음, 최대 25개 문서 |
| 초기 검색 쿼리 | 충분성 판단을 통과한 사건 설명의 요약 |
| 후속 검색 쿼리 | `summarize_context(fixed_case_context + "\n" + question)` |
| 후속 RAG 적용 | 항상 (판단 단계 없음) |
| 생성 입력 | 사건 요약 + 이력 요약 + 검색 문서 + 질문 |

목표 1은 컬렉션별 top-K로, 목표 2는 후속 쿼리에 고정 사건 요약이 항상 포함되는 것으로 구조적으로 충족된다. 검색 정확도와 답변 품질 수치는 레포에서 확인되지 않는다.

### 4.3 비교 실험

| 버전 | 검색 쿼리 | 필터 / top-K | 후속 질문 처리 | 코드에서 확인되는 동작 |
|---|---|---|---|---|
| 13 | 매 입력 원문 | 거리 ≥ 0.5 / 3 | 전체 이력 + 검색 결과 | 실행마다 컬렉션 삭제 후 재생성해 비어 있음, 필터 방향 반대 |
| 14·15 | 첫 상황 설명 | 거리 ≥ 0.3 / 3 | 전체 이력 | 검색 결과가 `messages`에 들어가지 않아 RAG 비활성 |
| 16 | 누적 상황 설명 | 거리 ≥ 0.5 / 3 | 첫 자문 1회만 RAG | 충분성 판단 도입, 컬렉션 삭제 제거 |
| 22 | 누적 상황 설명 | 없음 / 3 | 16과 동일 | 임계값 제거, 문서가 없으면 GPT 일반 지식 허용 |
| 23 | 누적 상황 설명 | 없음 / 3 | 16과 동일 | "오로지 참고 문서에 기반" 프롬프트 |
| 24 | 후속 질문 원문 | 없음 / 초기 10, 후속 5 | GPT가 RAG 필요 여부 판단 | 후속 질문도 사건 설명에 누적, 판례 컬렉션 경로가 QA 폴더를 가리킴 |
| 25 | 고정 요약 + 질문 | 없음 / 초기 10, 후속 5 | 판단 유지, 이력 GPT 요약 | 사건 고정, 이전 후속 질문 제외 |
| 26 | 요약(고정 요약 + 질문) | 없음 / 5 | 판단 제거, 항상 RAG | 요약 프롬프트에 "법적 쟁점이 드러나도록", "제품 이름·가격 배제" |
| 28 | 요약(고정 요약 + 질문) | 없음 / 5 | 26과 동일 | 요약 프롬프트가 "사실 중심 2~3줄"로 회귀, `ask_ai` 추가 |

생성 프롬프트의 근거 정책은 22(일반 지식 허용), 23(문서 기반만 허용), 26(문서 우선, "해당 없음" 금지) 순으로 바뀌었다. 근거 문서가 사건과 무관하면 엄격한 프롬프트는 빈 답을, 느슨한 프롬프트는 근거 없는 답을 만들므로 이 축은 검색 문제를 풀지 못한다. 코드 구조로 효과가 확인되는 변경은 쿼리에 사건 정보를 고정한 것(25)과 쿼리를 검색용 문장으로 재작성한 것(26)이다. 24·25의 RAG 판단 단계는 `NO` 오판 시 답변에 근거가 전혀 없고 그 자체로 GPT 호출을 1회 더하므로 26에서 제거했다.

## 5. 한계와 향후 과제

1. **정량 평가 부재.** 14·15의 버그도 답변만으로는 드러나지 않았다. 고정 질의 세트와 정답 문서 라벨로 컬렉션별 Recall@K를 측정하고, 매 턴 검색 쿼리·결과·프롬프트를 로그로 남겨야 한다.
2. **이전 후속 질문 참조 불가.** 쿼리가 "고정 사건 + 현재 질문"만 쓰므로 "아까 말한 그 조항" 같은 질의는 맥락을 잃는다. 대화 이력과 현재 질문을 함께 받아 독립 질의로 재작성하는 condense-question 단계가 필요하다.
3. **요약 길이와 토큰 제한 불일치.** 이력 요약 프롬프트는 600자 이내를 요구하지만 `max_tokens=100`이라 잘릴 수 있다. 26의 쟁점 중심 재작성 프롬프트가 28에서 빠진 것도 복원 대상이다.
4. **전역 상태.** `ask_ai`의 상태가 모듈 전역이라 그대로 호출하면 모든 사용자가 한 상담을 공유한다. 세션 분리 여부는 레포에 없는 서버 코드라 확인되지 않는다.
5. **페르소나와 단정 표현.** 최종 프롬프트는 "15년 경력의 전문 변호사" 페르소나와 "법적으로는 명확히 ○○죄에 해당됩니다" 같은 어조 예시를 쓴다. 13의 "위법성 단정 금지" 규칙과 반대 방향이며 근거 기반 상담 목표와 충돌한다.
